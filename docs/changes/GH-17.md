## Propósito

Hoy `devflow` solo se ejecuta con `npm start -- <args>` (vía `tsx`) desde la carpeta del repo, porque `tsc` corre con `noEmit` y no existe `bin`. Este cambio añade un `build` que genera JavaScript ejecutable y un `bin` que expone el comando `devflow`, para que un desarrollador del equipo pueda instalarlo y usarlo desde cualquier carpeta.

## Criterios de aceptación de origen

- CA1: `npm run build` genera `dist/` con `templates/` y las migraciones copiadas.
- CA2: `devflow --help` funciona tras instalar (`npm link` o instalación global).
- CA3: el mensaje final de `devflow config` («Siguiente paso: devflow config proyectos…») nombra un comando que existe.
- CA4: «Build / test commands» de `CLAUDE.md` actualizado.

**Hallazgos del refinamiento** (verificados con un build de prueba fuera del repo, en el directorio temporal de la sesión):

1. *(ambiguo)* **CA1 pide copiar `templates/` a `dist/`, y eso no es necesario ni correcto con el código actual.** Los módulos leen `templates/` y `package.json` con rutas relativas al módulo (`../../../templates/…`, `../../package.json`). Compilando con `rootDir: src` y `outDir: dist`, la profundidad se conserva: desde `dist/services/filesystem/` esa ruta sigue llegando a `templates/` de la raíz del paquete. Comprobado: `node dist/tui/cli.js --help` funciona sin copiar nada de `templates/`. Copiarlo a `dist/templates/` no serviría (nadie lo leería). Lo que **sí** falta es el directorio de migraciones: `tsc` no emite los `.sql` y `sqlite-storage-manager.ts:46` lo lee desde `./migrations/`, así que el primer uso con base de datos fallaría. Propuesta: leer CA1 como «tras el build, el programa encuentra `templates/` y las migraciones». `templates/` viaja con el paquete mediante `files` en `package.json`, y solo se copian las migraciones. Alternativa descartada: cambiar las rutas en cuatro módulos.
2. *(ambiguo)* **Error real de arranque por enlace simbólico.** `cli.ts` solo ejecuta `main()` si `import.meta.url` coincide con `process.argv[1]`. Con un `bin` enlazado simbólicamente (el caso de `npm link` en Linux y macOS), Node no resuelve el enlace en `argv[1]` y `main()` **no corre: sale con código 0 y sin ninguna salida**. Lo reproduje. En Windows el `.cmd` que genera npm suele pasar la ruta real, pero no lo he comprobado. Propuesta: resolver la ruta real con `realpathSync` en esa comparación (un cambio pequeño en `src/tui/cli.ts`; ningún test aprobado ejecuta esa rama, comprobado con búsqueda). Es lo que hace verificable E2. Necesita tu OK porque toca código de TK-03a.
3. *(asumido)* **Archivo `tsconfig.build.json` nuevo, sin tocar `tsconfig.json`.** `tsconfig.json` debe seguir con `noEmit` y cubriendo `tests/` para el `typecheck`. Autorizaste modificar `tsconfig.json`, pero un archivo nuevo es otra cosa: necesito que lo confirmes.
4. *(asumido)* **`scripts/copy-assets.mjs` nuevo y carpeta `scripts/` que `docs/002` §2.3 no lista.** Es un script de Node (no `cp`) para que el build funcione en Windows. Alternativa: la copia dentro de una orden de `npm` con `node -e`, más difícil de leer y probar.
5. *(asumido)* **Shebang en `cli.ts`.** `tsc` lo conserva en el JavaScript emitido; `tsx` lo acepta; en Windows se ignora. Sin él, `bin` no funciona en Linux ni macOS.
6. *(asumido)* **`files` en `package.json`** (`dist` y `templates`) para que una instalación global incluya lo que el código lee. `private: true` se mantiene (no impide `npm link` ni `npm install -g .`; solo evita publicar).
7. *(asumido)* **El test construye en un directorio temporal** (con `tsc` programático, 60 s de tiempo límite) y monta ahí `dist/`, `templates/`, `package.json` y `node_modules` enlazado, para no depender de que exista `dist/` en el repo ni escribir en él. Hace más lenta la suite (unos segundos).
8. *(asumido)* **No se añade `prepare`** (build automático al instalar): las instrucciones de #18 dirán `npm run build` antes de `npm link`. `npm start` (con `tsx`) se conserva para desarrollo.
9. *(asumido)* **Fuera de este cambio:** verificar `npm link` o instalación global y el `.cmd` real en Windows (issues #19 y #20) y redactar las instrucciones de instalación en `docs/001` §1.4 y `README` §1.4 (issue #18).

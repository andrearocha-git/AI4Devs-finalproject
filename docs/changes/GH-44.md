# Change: GH-44 — Fase 1: conservar la historia de usuario y los criterios Gherkin con el formato wiki de Jira

- **Estado:** Implementado
- **Fuente:** issue de GitHub [#44](https://github.com/andrearocha-git/AI4Devs-finalproject/issues/44) (milestone «Hito 3 — Listo para usar y entregar»; etiquetas `tipo:deuda`, `prio:should`, `dfc`, `necesita-autorizacion`). Origen: hallazgo de la prueba de aceptación en Windows (issue #20, paso 1) y `docs/002-arquitectura-del-sistema.md` §2.2 (Ollama AI Transformer).
- **Depende de:** GH-20 / issue #20 (hecho: la prueba que destapó el defecto). Toca TK-02e (transformer y posprocesado), ya implementado.
- **INVEST:** Cumple con observación (I: sin dependencias abiertas; S: 3 escenarios y 5 tareas, en el límite; T: el comportamiento determinista se verifica con tests; la mejora real del modelo solo se comprueba a mano con Ollama, ver punto 6). La etiqueta `necesita-autorizacion` va a Prerrequisitos.

## Propósito

Con tickets en el formato normal del equipo (wiki de Jira, con *Como / quiero / para* y *Dado / Cuando / Entonces*), la Fase 1 sale con la historia de usuario en «No especificado en el ticket.» y con los escenarios vacíos. Este cambio limpia el wiki antes del prompt, rescata de forma determinista lo que el modelo no asocia y evita que un escenario vacío llegue al documento como si estuviera completo.

## Criterios de aceptación de origen

- CA1: el formato wiki de Jira se limpia antes de enviar la descripción a Ollama, con un test.
- CA2: un ticket con «Como … quiero … para …» completos conserva la historia de usuario en la Fase 1.
- CA3: con criterios escritos como *Dado / Cuando / Entonces*, cada escenario sale con `Given`, `When` y `Then` rellenos.
- CA4: un escenario con `given`, `when` y `then` vacíos no llega al documento como si estuviera completo.
- CA5: hay un ticket de ejemplo en `tests/fixtures/tickets/` con el formato wiki real, y se comprueba con Ollama real que el resultado mejora. *(El ticket de ejemplo lo cubre E1; la comprobación con Ollama real es manual: ver «Decisiones y desvíos» y el punto 6.)*

## Escenarios BDD

### E1 — El formato wiki se limpia antes de enviar la descripción a Ollama (cubre: CA1, CA5)

- **Given** el ticket de ejemplo `tests/fixtures/tickets/historia-wiki.json`, con la descripción en formato wiki real de Jira (`*Como* nuevo usuario, *quiero* …`, `h3. *Criterios de Aceptación*`, `h4. *1. Registro exitoso (**_Happy Path_**)*` y viñetas `* *Dado* que …`)
- **When** el transformer arma la petición a Ollama para ese ticket
- **Then** el prompt enviado ya no contiene marcas wiki (`*…*`, `_…_`, `hN.`, viñetas `*` pegadas al texto) pero conserva el texto (la historia y los Dado / Cuando / Entonces, con las viñetas como líneas con guion), mientras que la descripción original del ticket y el texto crudo del fallback no cambian

### E2 — La historia de usuario completa no se pierde (cubre: CA2)

- **Given** un ticket cuyo texto trae «Como … quiero … para …» y una respuesta de Ollama con `quiero` y `para` correctos, `como` vacío y `presenteEnTicket.historiaUsuario` en `false`
- **When** se posprocesa la Fase 1
- **Then** la historia conserva `quiero` y `para`, `como` se recupera del texto del ticket, `presenteEnTicket.historiaUsuario` queda en `true` y no se agrega la pregunta abierta «¿Quién necesita esto, qué quiere y para qué?»; y si el ticket realmente no trae historia, sigue sobrescribiéndose con «No especificado en el ticket.»

### E3 — Los escenarios salen con Given / When / Then rellenos, o no salen (cubre: CA3, CA4)

- **Given** un ticket con criterios *Dado / Cuando / Entonces* y una respuesta de Ollama con escenarios con título pero con `given`, `when` y `then` vacíos
- **When** se posprocesa la Fase 1
- **Then** cada escenario que se puede recuperar del texto del ticket sale con `given`, `when` y `then` rellenos; un escenario con los tres campos vacíos que no se puede recuperar se descarta, y si no queda ninguno, `escenarios` queda ausente con su pregunta abierta; además, el prompt de sistema de historia indica que *Dado / Cuando / Entonces* equivalen a *Given / When / Then* y *Como / Quiero / Para* a la historia de usuario

- **2026-11-15 — E1, RED y mutación:** RED real (módulo `jira-wiki` inexistente y 2 casos del prompt fallando; otros 2 casos del transformer son guardas de regresión que ya pasaban: el original y el fallback no cambian). - **2026-11-15 — E1, desvío (pendiente de validar):** el contrato asumía limpiar también `{{monoespaciado}}` (punto 3). Un test aprobado de TK-02e («no vuelve a expandir marcadores que vengan dentro del texto del ticket», `ollama-ai-transformer.test.ts`) usa `{{descripcion}}` en la descripción y se rompía. Para no tocar ese test, **`{{…}}` no se limpia** (queda como el wiki sin soporte: tablas, `{code}`, `{panel}`). Es raro en tickets reales. `jira-wiki.test.ts` lo fija con un caso.

**Puntos ambiguos o asumidos al refinar (a confirmar por el desarrollador):**

1. *(ambiguo)* **Enfoque.** El issue ofrece cuatro ideas «a decidir al refinar». Por defecto: limpiar el wiki, explicar las equivalencias en el prompt **y** rescatar de forma determinista, desde el texto limpio del ticket, la historia (`Como … quiero … para …`) y los escenarios (`Dado / Cuando / Entonces`) que el modelo deja vacíos. Sin el rescate, CA3 depende solo de que un modelo de 3b obedezca el prompt, lo que ya falló. La alternativa (que el código extraiga también el resumen y las preguntas) queda fuera.
2. *(asumido)* **Dónde se limpia.** Solo en el prompt que va a Ollama, para **historias y bugs**. `ctx.description`, el texto crudo del fallback y la comparación de `verificarLiterales` de los bugs siguen usando el texto original; el rescate usa el texto limpio.
3. *(asumido)* **Sintaxis wiki que se limpia:** `*negrita*`, `_cursiva_`, encabezados `hN.`, viñetas `*` y `#`, `{{mono}}` y enlaces `[texto|url]`. Lo demás (tablas, `{code}`, `{panel}`) se deja como está. Se mantienen los números y los textos entre comillas, porque `verificarLiterales` los usa.
4. *(asumido)* **Palabras clave que se rescatan:** *Dado / Cuando / Entonces* y *Given / When / Then* (con *Y* como continuación), y *Como / Quiero / Para*. No se cubren otras formas de escribir la historia.
5. *(asumido)* **CA4 vale para historias y bugs**, porque ambos esquemas tienen `escenarios` con `given`, `when` y `then`.
6. *(ambiguo)* **CA5, «con Ollama real».** No es automatizable (el modelo no es determinista y los tests usan un Ollama simulado), así que no se declara escenario `Sin test`. Se hace a mano al final, con el Ollama de WSL y el ticket real de la prueba en solo lectura, y se anota el antes y el después en «Decisiones y desvíos».
7. *(ambiguo)* **`historia-v2`.** Subir la versión (regla de `templates/README.md`) obliga a cambiar dos filas de un test aprobado. Alternativa: no subirla y aceptar que `ticket_logs` mezcle resultados de dos prompts distintos bajo `historia-v1`. Por defecto se sube.
8. *(asumido)* **Fuera de este cambio:** `verificarLiterales` en historias (hoy solo en bugs), el progreso del streaming (#35), la causa del fallo de Ollama en `ticket_logs` (#31) y «No especificado» en las demás listas vacías (#37).

# Change: GH-55 — Instalador y actualizador para Windows (`scripts/install.ps1`)

- **Estado:** Implementado
- **Fuente:** issue de GitHub [#55](https://github.com/andrearocha-git/AI4Devs-finalproject/issues/55) (sin milestone; etiquetas `tipo:ticket`, `prio:should`, `dfc`).
- **Depende de:** #17, #18 y #19 (`build`, `bin`, instrucciones y verificación de la instalación manual), ya cerrados.
- **INVEST:** Observaciones: T. (I: sin dependencias abiertas; S: 3 escenarios y 5 tareas.) T: la lógica de decisión del script se prueba con tests automáticos, pero el recorrido completo (`npm install`, `build`, `npm link`) solo se puede comprobar a mano en Windows 11.

## Propósito

Hoy instalar DevFlow CLI exige `git clone`, `npm install`, `npm run build` y `npm link` a mano, y actualizar exige `git pull`, `npm install` y `npm run build`. Este cambio añade un script de PowerShell que comprueba los requisitos, instala o actualiza con un solo comando y no pisa trabajo local.

## Criterios de aceptación de origen

- CA1: comprueba Node ≥ 22.13, Git y Ollama activo con `qwen2.5:3b`; si falta algo lo dice con el paso a seguir y no continúa (en el caso de Ollama, solo avisa).
- CA2: sin instalación previa clona el repositorio, ejecuta `npm install`, `npm run build` y `npm link`, y comprueba `devflow --help`.
- CA3: con instalación previa compara con `origin`; si no hay cambios lo dice, y si los hay actualiza (`git pull --ff-only`, `npm install`, `npm run build`) y muestra la versión nueva.
- CA4: si el clon tiene cambios locales o el `pull` no es de avance rápido, se detiene sin pisar nada.
- CA5: probado en Windows 11 (PowerShell 5.1, `cmd` y PowerShell 7); queda anotado dónde.
- CA6: actualizados README §1.4, `docs/001` §1.4, `docs/002` §2.4 y `docs/009` (la decisión «sin instalador» deja de valer).
- CA7: decidido y anotado qué pasa con la comprobación de versión de Node que `docs/009` §1.1 y `docs/002` §2.2.1 dicen que existe: se implementa o se corrige el texto.

## Escenarios BDD

### E1 — Los requisitos se comprueban antes de tocar nada (cubre: CA1)

- **Given** un equipo con una versión de Node anterior a 22.13, o sin Git en el `PATH`, o con Ollama apagado o sin el modelo `qwen2.5:3b`
- **When** el instalador comprueba los requisitos
- **Then** si falta Node ≥ 22.13 o Git, muestra qué falta y el paso a seguir y termina con código distinto de 0 sin clonar ni compilar; si solo falta Ollama o el modelo, avisa con el comando a ejecutar (`ollama pull qwen2.5:3b`) y continúa

### E2 — El estado del clon decide si instalar, no hacer nada, actualizar o detenerse (cubre: CA2, CA3, CA4)

- **Given** una carpeta de instalación que (a) no existe, (b) es un clon al día con `origin`, (c) es un clon con commits nuevos en `origin` y sin cambios locales, (d) es un clon con cambios locales sin guardar, o (e) es un clon cuya rama local divergió de `origin`
- **When** el instalador determina qué hacer
- **Then** en (a) decide clonar e instalar; en (b) informa de que ya está al día y no cambia nada; en (c) decide actualizar con `git pull --ff-only` y mostrar la versión nueva; en (d) y (e) se detiene con un mensaje que explica el motivo, sin tocar el árbol de trabajo ni la historia

### E3 — La documentación refleja el instalador y la comprobación de Node (cubre: CA5, CA6, CA7)

- **Given** `scripts/install.ps1` terminado
- **When** se revisan README §1.4, `docs/001` §1.4, `docs/002` §2.4 y §2.2.1 y `docs/009` §1.1
- **Then** describen el instalador (un comando para instalar y actualizar) y ya no dicen «sin instalador»; el texto sobre la versión de Node es verdadero (dice quién la comprueba); y `docs/009` registra dónde y cuándo se probó el script en Windows 11

**Registro al implementar E2 (2026-11-16):**

**Hallazgo en la prueba en Windows 11 (2026-11-16), aprobado por la desarrolladora:**

- **Qué pasó:** tras una instalación nueva correcta, la segunda ejecución del instalador se detuvo con «cambios locales sin guardar». `git status` mostraba solo ` M package-lock.json` (3 líneas añadidas): `npm install` lo reescribe según la versión de npm. Los tests no lo detectaron porque sus clones nunca ejecutan `npm install`.
- **Decisión:** después de `npm install`, el instalador restaura `package-lock.json` con `git checkout -- package-lock.json` (`Restore-LockfileTrasNpm`). Es seguro porque el clon estaba limpio justo antes. Alternativas descartadas: ignorar el archivo en la comprobación (el `pull` fallaría si `origin` también lo cambia) y usar `npm ci` (falla si el lock no coincide con `package.json`).
- **Cómo se hizo:** RED con 3 casos nuevos en `install-ps1.estado.test.ts` (restaura y el clon queda al día; no toca otros cambios; sin `package-lock.json` no falla). **Mutación temporal (revertida):** quitar el `checkout` hace fallar el primer caso. Suite: **39 archivos y 856 tests** (se actualizaron las cifras, como se aprobó).

**Cierre de la tarea 3, prueba en Windows 11 (2026-11-16):**

- **Entorno:** Windows 11 (build 10.0.26200), Windows PowerShell 5.1.26100 y PowerShell 7.7.0, `cmd`, con un `origin` local y con el repositorio real de GitHub.

# Change: TK-03b1 — `devflow start`: validación, selección de ticket y repositorio

- **Estado:** Implementado
- **Fuente:** `docs/006-tickets-de-trabajo.md` (TK-03b1)
- **Depende de:** TK-02f, TK-02h y TK-03a (hechos y fusionados). Usa el contrato `StepResult` de TK-02a y los métodos `listAssignedTickets`, `listRepositoriesForTicket`, `listProjects` y `startTicket` del Orquestador.
- **INVEST:** Cumple. Cuatro criterios en tres escenarios y cuatro tareas; las dependencias están hechas. Observación (no es una letra que falle): `startTicket` necesita los ganchos `onStep` y `ask` de TK-03b2 y TK-03b3, que aún no existen; ver decisión 1.

## Propósito

Registrar `devflow start [ID] [--base <rama>] [--reprocesar]` en el `cli.ts` de TK-03a y resolver todo lo que ocurre **antes** de llamar a `startTicket`: validar el ID, elegir el ticket si no se dio, elegir el repositorio y avisar si no hay ninguna clave configurada. Deja listo el punto de entrada del Hito 2 sin que la TUI toque Jira, Git, Ollama ni SQLite.

## Criterios de aceptación de origen

- CA1: un ID de formato inválido (vacío o sin guion) no invoca al Orquestador y muestra un mensaje de validación; con un ID de una clave no configurada, se muestra el mensaje del Orquestador con las claves disponibles. *(CA1 del TK-03b original)*
- CA2: sin ID, se muestra la lista de tickets asignados que devuelve el Orquestador y se continúa con el elegido. *(CA2)*
- CA3: antes de llamar a `startTicket`, con varios repositorios la TUI pide elegir uno; con uno solo lo preselecciona; sin repositorios no muestra la selección y no pasa `repositoryId`. *(CA4 del TK-03b original; aquí es CA3 por numeración local)*
- CA4: sin ninguna clave de proyecto, `devflow start` indica «primero configura una clave» y no consulta a Jira. *(US-01 CA6)*
- DoD-a: la TUI no importa clientes de Jira/Git/Ollama ni el storage manager (revisión de imports y `npm run lint`).
- DoD-b: `--base` y `--reprocesar` llegan a `startTicket` como `baseBranchOverride` y `reprocessFase1`.
- DoD-c: revisión de código aprobada y mergeada (se tilda tras la merge; no es un escenario).

CA3 y CA5 del TK-03b original (carga manual y confirmación) pertenecen a TK-03b2; CA6-CA8 (progreso y pantallas), a TK-03b3: quedan **fuera de este cambio**.

## Escenarios BDD

### E1 — Validación del ID y aviso de «sin claves» (cubre: CA1, CA4)

- **Given** un Orquestador simulado con claves de proyecto (`SCRUM`) y otro sin ninguna, y unos prompts simulados
- **When** se ejecuta `devflow start` con un ID vacío, `SCRUM`, `12`, `-5` o con espacios en medio, con `scrum-2` y `A-1` (válidos), con `ABC-1` de una clave no configurada, y con un ID válido cuando no hay ninguna clave
- **Then** los IDs mal formados fallan con un mensaje de validación (que muestra el ejemplo `SCRUM-12`) **sin invocar nada del Orquestador**; `isValidTicketId` aplica el mismo criterio que el Orquestador (`^[A-Za-z][A-Za-z0-9_]*-\d+$` sobre el texto recortado); `scrum-2` y `A-1` pasan; con `ABC-1` se muestra el mensaje que devuelve `listRepositoriesForTicket` (las claves disponibles) y no se llama a `startTicket`; sin claves configuradas se avisa «primero configura una clave» (con el comando `devflow config proyectos`) y no se llama a `listAssignedTickets` ni a `startTicket`; en todos esos cortes el comando falla con el mensaje (código de salida 1) y no con una traza

### E2 — Sin ID: lista de tickets asignados (cubre: CA2)

- **Given** un Orquestador simulado con claves configuradas, cuyo `listAssignedTickets` devuelve tres tickets, una lista vacía o un fallo (token inválido, Jira sin respuesta), y un `TicketSelectionPrompt` simulado que elige uno
- **When** se ejecuta `devflow start` sin ID
- **Then** el prompt recibe exactamente los tickets del Orquestador (ID, título y tipo) y el ID elegido sigue al paso del repositorio y a `startTicket`; con lista vacía se informa «no tienes tickets asignados» y se termina sin error ni llamada a `startTicket`; un fallo de Jira se traduce con `describeFailure` (un token inválido no se presenta como «no existe») y no se llama a `startTicket`; con un ID dado en la línea de comandos no se llama a `listAssignedTickets`

### E3 — Repositorio, flags y registro del comando (cubre: CA3, DoD-a, DoD-b)

- **Given** un Orquestador simulado cuya clave tiene dos repositorios, uno solo o ninguno, un `RepositorySelectionPrompt` simulado, y el programa armado con `buildProgram` y `createHandlers`
- **When** se ejecuta `devflow start SCRUM-12 --base develop --reprocesar` con cada caso de repositorios, `devflow start` sin flags, y `devflow --help`
- **Then** con dos repositorios se pide elegir y `startTicket` recibe el `repositoryId` elegido; con uno solo se preselecciona sin mostrar el prompt; sin repositorios no se muestra el prompt y la entrada de `startTicket` **no lleva la clave `repositoryId`**; `--base develop` llega como `baseBranchOverride` y `--reprocesar` como `reprocessFase1: true`, y sin flags ninguna de las dos claves aparece; `startTicket` recibe además los ganchos `onStep` y `ask` que entrega el programa; la ayuda de `devflow` lista `start` con sus dos opciones; un Ctrl+C en cualquier prompt termina en silencio con código 130, como los demás comandos; y `npm run lint` pasa sin que `src/tui/` importe `database/`, `services/jira|git|filesystem|ollama/` ni `sqlite-storage-manager`

## Decisiones y desvíos

_Sin registros._

**Decisiones aprobadas por la desarrolladora (2026-11-12), tal cual se propusieron:**

1. *(ambiguo)* **Ganchos provisionales.** `startTicket` exige `onStep` y `ask`, que construyen TK-03b2 y TK-03b3. Propuesta: `runStart` recibe los ganchos por inyección (así los tests los simulan) y `createHandlers` pasa unos **provisionales**: `onStep` no hace nada y `ask` lanza «`devflow start` aún no está completo (faltan TK-03b2 y TK-03b3)». Hasta fusionar los tres, `npm start -- start` real se corta en ese punto. Los provisionales se reemplazan en b2 y b3.
2. *(ambiguo)* **Resultado de `startTicket`.** Este ticket no lo muestra (es de TK-03b3); `runStart` lo devuelve para que los tests lo comprueben.
3. **Salida y código de error.** Los cortes con problema (ID inválido, clave no configurada, sin claves, fallo de Jira) lanzan un `Error` con el mensaje, que `buildProgram` ya muestra por stderr con código 1. La lista vacía es informativa: mensaje por `out` y código 0.
4. **Orden de las comprobaciones.** Primero el formato del ID (sin Orquestador), después `listProjects` (sin claves → aviso), después el resto. Así CA1 y CA4 no se pisan.
5. **`HandlerDeps` con campos opcionales.** Los prompts de selección van como campo opcional de `HandlerDeps` (por defecto, los reales de `@inquirer/prompts`) para no cambiar los tests de `createHandlers` ya aprobados.
6. **Adaptadores de `@inquirer/prompts`.** Los dos archivos `*.prompt.ts` son adaptadores finos sin lógica propia, como `createInquirerPrompts` de TK-03a: no tienen escenario ni test propios; su lógica se prueba por la interfaz simulada.

**Desvíos registrados al implementar (2026-11-12):**

7. **Test aprobado modificado con autorización expresa (opción A).** Registrar `start` en `buildProgram` obliga a cambiar dos cosas de `tests/unit/tui/cli.test.ts`, ya aprobado en TK-03a: el test «registra solo `config`, con el subcomando `proyectos`» pasa a «registra solo `config` (con el subcomando `proyectos`) y `start`» y espera `["config", "start"]`; y el `setup()` añade `start: vi.fn(async () => {})` a los manejadores. El resto del archivo no se tocó; lo demás de E3 son casos nuevos. Esto desvía lo que decía la tabla de «Archivos afectados» («solo se añaden casos»).
8. **Cableado de `start` en `createHandlers`.** Para no cambiar los tests de `createHandlers` ya aprobados (cuyo Orquestador falso solo cubre `config`), `HandlerDeps` gana dos campos **opcionales**: `getStartOrchestrator` (perezoso; `main` lo entrega) y `startPrompts` (por defecto, los reales). Sin `getStartOrchestrator`, `start` falla con «no está disponible en esta configuración» en lugar de una excepción cruda.
9. **Ganchos provisionales** (decisión 1 aprobada): `onStep` no hace nada y `ask` lanza «`devflow start` aún no está completo: faltan TK-03b2 … y TK-03b3 …». Viven como constante `provisionalHooks` en `src/tui/cli.ts` y se reemplazan en TK-03b2 y TK-03b3.
10. **Adaptadores de inquirer sin test propio** (decisión 6 aprobada): `createTicketSelectionPrompt` y `createRepositorySelectionPrompt` son adaptadores finos sin lógica; su comportamiento se prueba por la interfaz simulada.
11. **Mutaciones de comprobación.** Tres casos de E3 y uno de E2 salieron en verde a la primera; se comprobó con mutaciones temporales (repositoryId siempre presente, `reprocessFase1` sin flag, Orquestador de `start` pedido de forma anticipada, lista de asignados pedida con ID dado) que los tests fallan; el código se restauró.
